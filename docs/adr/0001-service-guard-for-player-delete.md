# Delete protection lives in the service, not the foreign key

Whether a player can be deleted while bills still reference them is guarded by `deletePlayer` in the players service, not by the database. On 2026-09-03 we tried to move this guarantee into the schema by changing `bill_players.player_id` from `ON DELETE SET NULL` to `ON DELETE RESTRICT`. That change made drizzle-kit emit a full table rebuild, and the rebuild wiped four tables. Drizzle's migrator runs statements inside a transaction, where SQLite ignores `PRAGMA foreign_keys=OFF`, so dropping the parent table fired the children's `ON DELETE CASCADE` and erased `item_allocations`, `adjustment_allocations`, `payment_statuses`, and `payment_events` on the live database. Recovery came from a `deploy/backup.ts` snapshot taken minutes earlier. We reverted to `SET NULL` and deleted the migration.

## Consequences

- SQLite cannot change a foreign key action without rebuilding the table, so "just change the FK" is off the table while any child table cascades from it. Any generated migration that drops or recreates a table gets audited first: check which tables reference it and with which actions.
- Applying a migration to `data/tabquest.db` always follows a fresh `just db-backup`, including when the application happens via a quadlet restart. The pre-incident backup is the only reason this was recoverable.
- Removing a bad migration from the repository does not remove it from the deployed image: the quadlets carry their own copy of `drizzle/` and re-apply whatever is in it at every startup. After deleting a migration, rebuild the image (`just image-build`) before restarting the services; the same night, a restart on the stale image wiped the restored tables a second time.
- Restoring a SQLite file requires zero open connections. A restore done while a dev server or container still held the file open let the stale connection's WAL checkpoint rewrite the wiped state over the restored data a third time. Use `just db-restore <backup.tar.gz>`, which refuses to run while any process holds `data/tabquest.db`, its WAL, or its SHM open, and restart services only after the restore is verified.
